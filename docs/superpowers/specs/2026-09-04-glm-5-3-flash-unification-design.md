# 企安用工 Desktop GLM-5.3-Flash 统一设计

**状态：** 用户已于 2026-09-04 批准

## 目标与边界

将智谱真实 Provider 的文本和视觉模型统一为官方模型编码 `glm-5.3-flash`。保留现有 API Key、固定智谱服务地址、本地脱敏、结构化事实校验、R01—R20、界面流程和安装包发布方式，不增加 Provider、模型选择器或新业务功能。

## 方案比较

1. 只修改前端默认值：改动最小，但旧配置、Python fallback 和手工请求仍可能继续使用旧型号，不能满足“全部统一”。
2. 前端隐藏两个字段：界面更简单，但如果后端仍接受任意模型值，不能形成可信边界。
3. 使用跨层统一常量并收敛设置界面：前端提交固定型号，Rust 配置层只接受固定型号，Python Provider 的文本和视觉 fallback 均为固定型号；旧配置必须重新验证。该方案改动集中、约束完整，采用此方案。

## 配置与迁移

- 设置页仅显示一个只读“分析模型：GLM-5.3-Flash”，不再暴露文本模型和视觉模型输入框。
- 前端保存设置时仍沿用现有 IPC 数据结构，`textModel` 与 `visionModel` 都提交 `glm-5.3-flash`，避免无关协议重构。
- Rust 配置层只接受两个模型字段均等于 `glm-5.3-flash`；服务地址仍只接受现有智谱固定地址。
- 对磁盘中保存了旧模型的配置，状态查询返回统一型号并将其视为“尚未完成当前模型连接验证”。用户重新输入自己的 Key 并点击“保存并测试连接”后，才写回统一型号并恢复真实分析入口。
- sidecar 环境变量只能收到 `AI_TEXT_MODEL=glm-5.3-flash` 和 `AI_VISION_MODEL=glm-5.3-flash`，不能从旧配置透传其他型号。

## Provider 数据流

文本、PDF/DOCX/XLSX 等解析后的文本内容继续走文本分支；图片继续走已有图片内容块分支。两个分支最终都调用 `glm-5.3-flash`。现有请求端点、图片 Base64 Data URL、脱敏边界、超时、重试、预算限制和响应 schema 不变。

## 错误与安全

- 旧配置不冒充已经验证过新模型；连接状态必须重新验证。
- API Key 继续只写入 macOS Keychain，不进入 React 状态、配置文件、日志、测试或仓库。
- 模型错误继续映射为现有稳定错误码，不向界面暴露凭据或原始 Provider 响应。

## 测试与验收

按红—绿—重构执行：

1. 前端测试先证明设置页只显示统一模型，并提交两个相同的固定模型值。
2. Rust 测试先证明任意非 `glm-5.3-flash` 配置会被拒绝，旧配置不会保持已验证状态，sidecar 环境只注入统一型号。
3. Python 测试先证明智谱 Provider 在空模型配置时，文本与视觉均 fallback 到 `glm-5.3-flash`；图片请求仍生成正确的多模态内容块。
4. 更新 README 和真实 Provider smoke 默认型号，扫描仓库中面向生产的旧型号残留。
5. 运行完整 Python、前端、Rust、敏感信息和公开历史校验；提交推送后监控 CI 与 RC 构建。
6. 最终安装包仍须使用用户自己的 Key 和完全虚构材料进行真实模型验收。通过前 PR #2 保持 Draft，且不合并。
